# 干草堆

**这个仓库现在有 1,582,400 个文件。其中 1,000,000 个是同一个字节。**

`haystack/` 下有 **1,000,000 个普通文件**，每一个的内容都恰好是 1 个字节 —— 全部是同一个字符 `x`，全部指向同一个 blob。

| | 之前 | 现在 | 变化 |
|---|---:|---:|---:|
| 工作树文件数 | 577,505 | **1,582,400** | **+174%** |
| 其中 `haystack/` | 0 | **1,000,000** | — |
| 仓库 `size`（GitHub 自己报的） | 16,204,685 KB | **16,253,074 KB** | **+0.3%** |
| 可达提交 | 1,636,947 | 1,637,025+ | +78+ |

**文件数涨了 1.74 倍，体积涨了千分之三。**

## 一、单价

| | 文件数 | 代价 | 每个文件 |
|---|---:|---:|---:|
| Linux 内核工作树 | ~80,000 | 6,068 MiB（仓库本体） | ~79,606 B |
| 这个 `haystack/` | **1,000,000** | **2.26 MiB**（本地 repack 实测） | **2.31 B** |

**单价差约 34,000 倍**（按 GitHub 自己报的 size 增量 3,051 KB 算，是 3.12 B/文件，仍然差 25,500 倍）。

对照上一轮的 `vigil`：提交数 119.80 B/个。**文件数便宜 52 倍。**

### 为什么这么便宜

git 是**双重内容寻址**的：

1. **blob** —— 那个 1 字节的 `x`，全仓库只存一次，被引用一百万次。
2. **tree** —— 一百万个条目，但每条都只是「另一个名字、同一个 blob」—— delta 压缩后几乎归零。

实测（本地，`python haystack.py measure --n 1000000`）：

```
1,000,000 个文件  →  打包后 2,261 KiB (2.26 MiB)
                     in-pack 只有 4 个 git 对象
                     = 每个文件 2.31 字节
```

**100 万个文件，4 个 git 对象。** 这就是内容寻址的极限。

## 四、踩到的三个坑（都很有用）

### 1. GitHub 的 API 无法重建这个仓库的根树

上游根树里有一个**文件名是一个空格**的文件：

```
100644 blob d35eef3419e44dcc4b063e226b184a0509bbbb40	 
```

`POST /git/trees` 会把它判定为 blank：

```
422 tree.path cannot be blank
```

**也就是说：任何想通过官方 API 重建这个仓库根树的尝试，都必然失败。**
这个仓库里恰好有一个 GitHub 表达不了的文件名。

### 2. `base_tree` 会让服务端展开整棵树，然后超时

```
POST /git/trees {base_tree: <上游根树>, tree: [1 个条目]}
→ 504，重试 4 次全失败
```

根树只有 210 个条目，但 GitHub 会**递归展开**它引用的全部子树（57 万文件）来做校验。
请求体只有几百字节，服务端的工作量是几百万条目。

### 3. 一次新增 1 条 tree 条目能过，一次新增 10 条不行

```
POST /git/trees {tree: [1 个 040000 条目引用 10 万条目的树]}   → OK  3.7s
POST /git/trees {tree: [10 个 040000 条目]}                    → 504 11.8s
```

**逐条累加（每次以 `base_tree` 指向上一次的结果）就全部成功。**
这是唯一能过 API 的路径 —— 但即使这样，最后建根树仍然被上面第 1 条堵死。

### 最终解法：不用 API 建树

树的本质就是字节：

```
<mode> <name>\0<20-byte sha>
```

- `git hash-object -w -t tree` 直接写 tree 对象，**不校验引用的对象是否存在**；
- `git mktree --missing` 用 git 自己的排序规则做同样的事。

于是全部对象在本地 1.2 秒内构造完成，`git push` 推上去 ——
**fork 与上游共享对象库**，根树引用的上游对象服务器本来就有，push 只带真正新的东西。

而内容寻址给了**免费的正确性校验**：
本地重建的 10 棵叶子树，sha 必须与之前用 API 建的一模一样。实测 10/10 全部一致。

## 五、边界

- **只增不改。** 没有修改或删除任何既有文件；没有冒充任何人。
- 作者是明确虚构的 `haystack@invalid.example`。
- **不可逆**：合并后要删掉这一百万条 tree 条目，只能重写历史。
- 工作树「新增内容」是 1,000,000 字节（1 MiB，全部是同一个 `x`）——
  但克隆/检出时它会被实例化成**一百万个 inode**，这是真实代价。
- GitHub 的网页端对 10 万条目以上的目录会拒载或极慢 —— 那是平台自己的上限。

## 六、它想说的话

Linux 内核的 8 万个文件，是三十多年里几万个人一个一个写的。

这里的 100 万个文件，是一台机器在 1.2 秒里算出来的，代价是仓库体积的千分之三。

**它们在任何一个只数文件数的界面上，看起来一样。**

而这一百万个文件加起来的**信息量，是 1 个字节。**
